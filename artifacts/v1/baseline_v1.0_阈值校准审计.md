# 当前baseline结果与v1.0验收阈值校准审计

版本：v1.0  
日期：2026-07-17  
数据来源：

- `evaluation/baseline/metadata.json`
- `evaluation/baseline/per_seed.csv`
- `evaluation/baseline/summary.csv`
- 当前`evaluate.py`、`train.py`、`network_env.py`与`pricing_manager.py`的指标实现

状态：旧机制诊断报告；不能作为v1.0正式性能基线

## 1. 结论摘要

这批结果可以回答“当前旧系统表现出什么统计特征”，但不能证明v1.0要求下的真实完成率、SLA、预约可靠性、经济成本和绿能收益。

最重要的结论：

1. 表中的`completion_rate=1.0`不是实际完成率，而是成功调度率；每个种子结束时仍有135至188个活动任务，评估没有排空。
2. `weighted_cost_ratio=1.29985`表示当前总成本约为基准的129.98%，即净成本高约29.98%；但`avg_cost_saving_ratio=14.42%`仍显示正节省，因为当前节省率把负节省截断为0。两者不能同时作为系统结论。
3. 任务动作绿电匹配率很高，均值94.78%，但系统绿电吸纳率只有34.98%，绿电闲置率65.02%。这证明“任务覆盖”和“系统吸纳”不能混为一个指标。
4. 当前`overload_event_rate=47.31%`不是容量超限率，而是候选节点预计利用率超过85%的事件率；不能用它验证CPU超容量事件为0。
5. 五种子下主成本指标的95%均值区间半宽约为12.18%。如果不使用相同任务轨迹的配对差，5%的成本改善无法被可靠识别。
6. 系统绿电吸纳率的95%区间半宽约为0.95个百分点，3个百分点的改善相对当前种子波动较容易识别；动作级吸纳率的区间半宽却约为3.24个百分点。
7. 模型文件哈希可复核，但缺少评估代码、任务轨迹、拓扑和依赖环境哈希，因此不能完整复现当时的测量语义。

## 3. 当前结果的真实含义

### 3.1 任务状态

五个种子平均：

| 当前字段 | 均值 | 实际含义 |
| --- | ---: | --- |
| `generated_tasks` | 4914.6 | 正式窗口生成的任务数 |
| `succeeded_tasks` | 4914.6 | 调度返回`Success`的任务数，不是Completed数 |
| `dropped_tasks` | 0 | 当前旧队列/重试规则下没有记录drop |
| `deferred_actions` | 260.6 | 旧独立WAIT动作次数 |
| `active_task_count` | 164.0 | 评估结束时仍在预约或运行的活动项 |
| `completion_rate` | 100% | `succeeded/(succeeded+dropped)`，实际为调度解决率 |
| `throughput_rate` | 100% | `succeeded/generated`，仍是调度成功口径 |

`EvaluationMetrics.record_success()`在环境返回调度成功时立即增加`succeeded`；`update_active_tasks()`在任务完成时只移除活动项，没有增加Completed计数。评估循环在任务轨迹结束后立即汇总，没有排空阶段。

所以：

```text
当前completion_rate != Completed / Arrived
当前throughput_rate != 完成吞吐率
```

不能用`4914.6-164.0`估算正式Completed数，因为活动任务可能包含预热任务，当前分配对象也没有记录任务来源和完成事件计数。

### 3.2 成本

| 指标 | 均值 | 解释 |
| --- | ---: | --- |
| `weighted_cost_per_cpu_time` | 0.0168980 | 当前开始时刻价格乘CPU工作量后的加权值，未做执行区间积分 |
| `weighted_cost_ratio` | 1.29985 | 总成本约为内部基准成本的129.98% |
| `avg_cost_ratio` | 1.48012 | 平均任务成本比为148.01% |
| `p95_cost_ratio` | 3.25120 | P95任务成本约为基准的325.12% |
| `avg_cost_saving_ratio` | 14.424% | 只保留正节省后的均值，不能表达净成本 |
| `cost_over_budget_event_rate` | 50.783% | 成本比超过配置预算线的动作比例 |

`weighted_cost_ratio>1`与正的`avg_cost_saving_ratio`并不是真实矛盾，而是统计口径不同：前者保留所有成本，后者对负节省使用`max(0, saving)`。正式报告必须以净经济成本和单位已完成CPU工作量成本为主，正向截断节省率只能作为分布辅助项，不能作为系统优化结论。

此外，旧实现把名为“元/MW”的价格换算后直接乘`CPU×仿真时长`，没有把仿真时长转换为小时；当前0.50~1.30数值也未明确是元/kWh还是相对指数。因此这些旧成本只能解释为内部成本指数或相对比值，不能解释为物理货币“元”。v1.0已通过F-06冻结：明确的元/kWh输入乘1000迁移为元/MWh；若旧值只是相对量则仅迁移为`cost_index`。运行代码尚未完成该迁移，必须重建成本账。

### 3.3 绿能

| 指标 | 均值 | 解释 |
| --- | ---: | --- |
| 动作绿能匹配率 | 94.784% | 被调度节点在计算开始时刻的绿电匹配快照 |
| 动作绿能吸纳率 | 54.636% | 被调度节点开始时刻的吸纳快照 |
| 系统绿能吸纳率 | 34.981% | 系统采样时刻吸收的绿电比例均值 |
| 系统绿电闲置率 | 65.019% | 与系统吸纳率互补 |
| 绿电负载覆盖率 | 93.692% | 计算负载大部分可以被绿电覆盖 |
| 绿电供需比 | 3.453 | 绿电供给整体显著高于当前电力需求 |
| 平均绿电使用 | 785.32 MW | 瞬时功率采样均值，不是MWh |
| 平均绿电供给 | 2449.05 MW | 瞬时功率采样均值 |
| 平均绿电闲置 | 1663.73 MW | 瞬时功率采样均值 |

当前场景的主要绿能问题不是“任务无法获得绿电”，而是供给远大于负载、系统有大量绿电闲置。因此：

- 只优化任务覆盖率很容易接近饱和；
- 只报告动作匹配率会掩盖系统吸纳不足；
- v1.0采用“任务覆盖+系统吸纳增量”的组合方向是必要的；
- 正式指标必须把MW快照改为完整执行区间的MWh积分。

### 3.4 负载与所谓overload

平均节点CPU使用率为35.876%，但`overload_event_rate`为47.306%。当前代码中的overload定义是：所选节点预计利用率超过85%后的归一化约束值，而不是超过100%物理容量。

因此该结果说明：

- 全局平均资源较空闲；
- 调度仍频繁选择高于85%利用率的局部节点；
- 可能存在明显热点或资源聚集；
- 不能据此宣称发生了47.3%的物理超容量事件；
- 正式报告应同时提供物理超容量事件、P95/最大节点利用率、热点持续时间和节点利用率离散度。

## 5. v1.0正式验收方法

### 5.1 三层判定

每个策略先后通过：

1. **硬机制门槛**：CPU/BW超容量、绝对SLA违规、部分预约、预约失效和未来信息泄漏全部为0；
2. **守门指标非劣效**：完成率以及没有作为主要优化目标的另一核心指标不能发生不可接受退化；
3. **主要目标改善**：成本或绿能至少一项同时达到统计显著和工程显著。

不允许把三层合并为一个奖励平均分。

### 5.2 配对差定义

对每个seed `r`，未来预约策略`P`与最早可行基线`B`使用完全相同任务轨迹：

```text
relative_cost_change_r = (cost_P_r - cost_B_r) / cost_B_r
green_coverage_change_r = coverage_P_r - coverage_B_r
green_absorption_change_r = absorption_P_r - absorption_B_r
completion_change_r = completion_P_r - completion_B_r
load_change_r = load_P_r - load_B_r
```

所有置信区间都基于这些逐seed配对差，而不是分别对两个策略的均值做肉眼比较。

### 5.3 初始工程阈值

| 指标角色 | 已确认阈值 | 统计条件 |
| --- | --- | --- |
| 真实完成率守门 | 相对基线下降不超过0.5个百分点 | 配对差95%区间下界不低于-0.5个百分点 |
| 成本作为改善目标 | 单位已完成CPU工作量经济成本降低至少5% | 平均配对变化≤-5%，且95%区间上界<0 |
| 成本作为守门目标 | 恶化不超过1% | 配对变化95%区间上界≤+1% |
| 绿能作为改善目标 | 任务覆盖或系统吸纳核心指标提高至少3个百分点 | 平均配对变化≥+3个百分点，且95%区间下界>0 |
| 绿能作为守门目标 | 核心指标下降不超过1个百分点 | 配对变化95%区间下界≥-1个百分点 |
| Soft/Flexible偏好按时率 | 第一轮分别报告；完成正确基线后再设质量阈值 | Soft `1.2L`、Flexible `1.5L`绝对上限违规仍必须为0 |
| P95节点利用率/负载离散度 | 恶化不超过2个百分点或事先定义的等价相对幅度 | 配对区间不得越过非劣界 |
| 物理超容量和预约失效 | 0 | 任一种子出现即失败 |

策略总体通过要求：

- 成本和绿能至少一项达到改善目标；
- 另一项满足守门目标；
- 完成率满足非劣效；
- 所有硬门槛为0；
- 结果不被最早可行基线Pareto支配。

### 5.4 种子数量和统计功效

当前5个种子只适合机制诊断，不适合冻结正式结论。

固定流程：

1. 先运行至少10个相同轨迹的配对种子作为pilot；
2. 用pilot的配对差标准差`σ_delta`计算正式所需种子数；
3. 以双侧α=0.05、统计功效80%估算：

```text
n >= ((z_0.975 + z_0.80) × σ_delta / practical_delta)^2
z_0.975 + z_0.80 ≈ 2.802
```

4. 正式实验原则上不少于10个种子，通常应准备20个以上；若功效分析要求更多，则按更大值执行；
5. 种子集合必须在查看策略结果前冻结。

以当前未配对的主成本标准差作保守近似，检测5%成本改善约需要25个配对种子；若采用两个互不配对的策略样本则约需49个种子/策略。实际同轨迹配对通常会降低`σ_delta`，最终数量必须由新机制pilot确定。

## 6. 当前baseline指标的处置

### 6.1 可保留为旧机制诊断

- 生成任务数和处理尝试数；
- 旧WAIT次数；
- 当前价格模型下的成本分布；
- 当前开始时刻绿能快照；
- 当前系统采样功率与绿能比例；
- 当前模型和配置的历史存档。

### 6.2 必须更名

- `succeeded_tasks` → `scheduled_success_tasks_legacy`；
- `completion_rate` → `schedule_resolution_rate_legacy`；
- `throughput_rate` → `schedule_success_per_arrival_legacy`；
- `overload_event_rate` → `selected_node_above_85pct_event_rate`；
- `avg_physical_latency` → 按当前实现明确为旧网络时延口径；
- `avg_end_to_end_latency` → 按当前实现明确为旧启动时延口径。

### 6.3 不得作为v1.0主结论

- 当前`completion_rate`；
- 当前`throughput_rate`；
- 正向截断的`avg_cost_saving_ratio`；
- 当前`overload_event_rate`作为物理超限率；
- MW快照作为任务绿能消耗量；
- 当前SLA零违规率作为新JIT和Soft双阈值模型的证据。

### 6.4 v1.0必须新增

- `Reserved/Transmitting/Running/Completed/Failed/Expired/Rejected/Pending`状态计数；
- `Completed/Arrived`真实完成率；
- `Completed/Reserved`预约可靠率；
- CPU与BW物理超容量事件；
- 原子预约部分提交事件；
- Soft偏好按时、可接受迟到和绝对违规；
- JIT传输区间和计算区间指标；
- 已完成任务完整区间经济成本；
- `seconds_per_sim_unit`、任务MW、任务MWh和`economic_cost_yuan`量纲审计列；
- `cpu_work_sim_units`与`cpu_work_cpu_hours`分列，主成本分母使用已完成CPU小时；
- 正式完整窗口的理论/实际时间槽数及`candidate_mode=complete`；
- 任务MWh、绿电MWh、绿能覆盖和系统吸纳增量；
- 最早候选与实际候选的反事实收益向量；
- 同任务轨迹的策略配对差和置信区间。

## 7. 正式baseline重新生成条件

只有以下条件全部满足后，才能生成名为`v1.0_baseline`的正式结果：

1. F-01至F-07和S-01至S-15已经冻结，需求与七个schema版本字段均为`"1.0"`；
2. 时间单位、传输模型和预约日历测试通过；
3. CPU/BW原子预约与状态机测试通过；
4. 评估可以停止到达、结算全部已到达Queued/Pending并排空全部已接受任务，正式结果末尾零非终态；
5. 成本和绿能按执行区间积分，且通过元/MWh×MW×小时的量纲与时间缩放不变性测试；
6. 指标schema带版本号；
7. metadata记录代码、模型、配置、拓扑、任务轨迹和依赖哈希；
8. 至少使用最早可行基线和一个未来预约策略运行相同任务轨迹；
9. 正式模式完整枚举窗口时间网格，未启用时间采样或候选Top-K；
10. 输出逐seed原始值、配对差、95%区间、工程门槛和硬门槛结果。
11. 任一策略seed运行无效时整组pair判无效并使正式机制验收失败，不允许单侧删除或事后替换seed。
