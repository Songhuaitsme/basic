# V2 调度策略评估体系

## 1. 判优原则

调度策略不存在脱离约束的单一“总分”。本系统按“结果指标 + 作用机制指标 + 护栏指标 + 运行效率指标”评价：

- 结果指标：完成率、单位完成 CPU 小时成本、任务绿电覆盖率、系统绿电吸收率、各 SLA 准时率。它们直接对应可靠交付、经济性、绿色能源利用和服务质量。
- 作用机制指标：主动等待、候选数量、任务时延、节点分配、链路使用。它们解释结果是如何产生的，不能脱离结果指标单独判优。
- 护栏指标：预留可靠性、过期/失败、CPU 超容量时间占比、未结算任务数。任一物理违规或不完整结算都会使报告失效，而不是用其他收益抵消。
- 运行效率指标：整体评估墙钟时间、决策总耗时、平均/P50/P95 单次决策耗时、候选生成、策略选择、模型推理和预留提交耗时。

指标方向必须由定义决定：成本、时延和违规率越低越好；完成率、绿电覆盖和 SLA 准时率越高越好；CPU 利用率、远程调度率、主动等待等只作诊断，不强行设为单调目标。正式判优应在相同 seed 上配对比较，并报告跨 seed 均值和配对置信区间；单 seed 只能作为点估计和系统验收依据。

## 2. 综合评价维度与指标

| 维度 | 核心指标 | 反映的能力 |
|---|---|---|
| 调度效果与可靠性 | 接受率、完成率、预留可靠性、拒绝/过期/失败数 | 是否能把到达任务转化为可靠完成 |
| 经济性 | 总归因成本、每完成/每到达 CPU 小时成本 | 是否以较少经济成本交付等量工作 |
| 绿色能源 | 完成任务绿电覆盖率、系统绿电吸收率、节点绿电覆盖 | 是否把负载放到绿电可用的节点和时段 |
| SLA | 分 SLA 类型的准时率、可接受迟到率、过期率、开始时延 P50/P95 | 是否满足不同服务等级及其长尾要求 |
| 任务时延 | 排队、预留、开始、完成时延的均值/P50/P95 | 局部调度决定对任务体验的影响 |
| 资源利用 | 时间-节点平均 CPU 利用率、P95/最大利用率、热点和超容量时间占比 | 资源是否充分且安全地使用 |
| 负载均衡 | 时间加权节点利用率 CV、节点 CPU 工作量 CV、节点分配占比 | 工作是否过度集中在少数节点 |
| 网络 | 远程任务率、传输时延、数据量、路径跳数/距离、链路利用率 | 计算放置带来的网络代价和拥塞风险 |
| 算法效率 | 评估墙钟、单决策均值/P95、候选生成、选择/推理、提交耗时 | 策略本身的计算开销和伸缩性 |

总成本使用守恒的任务归因账本；绿电指标同时保留任务视角和系统供给视角，避免只提高任务覆盖却浪费系统绿电；利用率由半开区间预留和配置容量精确积分，不使用采样点近似；墙钟指标只在同设备、相同审计模式、相同进程并发和相同候选配置下可比。

## 3. 四层评估

1. Task-level：`task_records` 保存每个任务的到达、决策、传输、计算、节点、路径、时延、CPU 工作量、成本和绿电；导出时再关联该任务的全部决策及账本记录。
2. Time-level：以所有计算/传输预留的起止时刻切分精确事件区间，每个区间记录活动任务数、节点 CPU 利用率、负载 CV 和链路利用率。时间加权汇总不会让短暂峰值与长时间低负载被简单平均。
3. Node-level：按节点汇总预留数、CPU 小时、分配占比、平均/峰值利用率、成本、能耗和绿电覆盖。
4. System-level：聚合完成、成本、绿电、SLA、吞吐和可靠性，同时保留前三层记录用于下钻解释。

系统级指标用于最终比较，细粒度指标用于定位差异。例如系统成本下降时，可沿“任务成本 → 目标节点 → 时间区间 → 当时节点利用率/绿电”追溯原因；如果系统均值相近，则可继续比较节点热点、任务 P95 时延和特定路径的网络负载。

## 4. 代码中的完整数据链路

```text
任务生成/冻结任务轨迹
  v1/evaluate_v1.py::_generate_trace
        ↓
三阶段执行（到达、准入结算、执行排空）
  v1/evaluation_v1/runner.py::EvaluationRunner.run_frozen_policy
        ↓
调度决策与资源预留
  v1/scheduler/v1_scheduler.py::run_cycle/_schedule_one
  v1/scheduler/resource_calendar.py::ReservationCalendar
        ↓
完成事件与成本/绿电账本
  v1/accounting/ledger.py::MetricsLedger
  v1/accounting/energy.py::ExogenousEnergyAccounting.realize
        ↓
系统指标与任务记录
  v1/evaluation_v1/metrics.py::build_seed_metrics
  v1/evaluation_v1/runner.py::_task_records
        ↓
四层诊断与运行效率
  v1/evaluation_v1/diagnostics.py::build_evaluation_diagnostics
  v1/profiling.py::TrainingPerformanceProfiler
        ↓
配对校验与 CSV 导出
  v2/export_five_policy_metrics.py::export_reports
        ↓
五策略对比和可视化
  v2/compare_five_policies.py::build_report_artifact
```

原始 JSON 是事实源。`metrics` 保存正式系统指标，`task_records` 和 `decision_records` 支持任务下钻，`accounting_report` 提供可守恒复核的经济/能源数据，`diagnostics` 保存四层派生指标及其定义。compact 模式只移除冗长的逐周期 `cycle_results`，不会移除任务、决策、账本或诊断数据。

## 5. 导出文件与可视化

- `metrics_long.csv` / `metrics_wide.csv`：系统指标和诊断汇总，供五策略统一比较。
- `task_metrics.csv`：每个 policy/seed/task 一行，包含任务结果、账本值和该任务决策耗时。
- `decision_metrics.csv`：每次决策一行，包含候选规模、选择结果、等待收益和墙钟耗时。
- `time_metrics.csv`：每个精确资源事件区间一行。
- `node_metrics.csv`：每个节点一行。
- `network_metrics.csv`：每条物理链路一行；旧报告只能回退为路径级传输统计。
- `runtime_metrics.csv`：每个 policy/seed 一行的运行效率明细。
- `source_manifest.csv` / `analysis_validation.json`：来源哈希、配对条件、有效性和各层覆盖情况。

报告对每个 policy 使用相同指标定义和单位。图表显示成本、绿电、可靠性、SLA、等待行为，并在数据可用时自动增加任务完成长尾、节点负载均衡、网络放置和单决策 P95 耗时。报告不会在单 seed 下伪造置信区间，也不会把诊断指标强行合成为一个“冠军分数”。

## 6. 当前使用步骤

当前阶段不运行多 seed。代码补齐后先用已有报告重建细粒度源表和 HTML；旧报告能得到任务、决策、节点分配和路径传输的安全子集，但时间利用率、链路容量利用率和墙钟效率只有重新生成的新报告后才完整出现。

```powershell
py -m v2.export_five_policy_metrics `
  --input-dir artifacts/v2/evaluation/five_policy

py -m v2.compare_five_policies
```

将来需要正式统计结论时，再固定未参与训练的多组 seed，用 `v2.evaluate_five_policies` 做相同任务轨迹的配对实验。届时必须固定模型、设备、候选块大小、审计模式、配置和依赖版本，并以报告中的哈希配对校验为准。
